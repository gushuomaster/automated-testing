# 第一阶段需求解析技术设计

## Context

参见 `proposal.md` 的动机。项目建设需求以仓库根目录的 `CS-Autonomous-Testing-Framework-v0.1.md` 为基线；MiniOrder 中文需求和 `技术要求.docx` 分别承担校准与开发验证角色，不反向定义项目范围。

`D:\project\agent\examples` 已存在 Python 3.11 `testing_platform` 骨架、需求 Pydantic 模型、AgentGateway、Hermes Gateway、SkillRegistry、测试工作流、任务与产物边界，以及历史需求提取基准。这些能力证明了平台骨架和“需求资料到结构化测试设计”链路可以运行，但当前实现仍把文档压成纯文本，将需求提取与用例生成混在同一工作流，缺少 PDF Adapter、Document IR、稳定来源定位、独立需求分析工作流和精确率/召回率评分。该目录同时存在大量用户未提交修改，因此只作为复用来源和验证证据，不直接在其中实施，也不作为正式系统的运行时依赖。

## Goals / Non-Goals

**Goals:**

- 在现有 `testing_platform` 分层和端口基础上补齐 DOCX、Markdown、PDF 解析与需求分析能力。
- 扩展而不是复制现有需求模型、Agent 端口、Skill 注册、任务和产物边界。
- 固定版本化的输入清单、文档片段、原子需求、核验结果和评估结果契约。
- 将格式解析、模型推理、核验和真值评分解耦，以便分别定位失败原因。
- 支持校准、开发验证和正式盲测三类运行，并保证评估真值不进入分析 Agent 的可见目录。
- 首版复用 Hermes 作为 Agent 运行时，同时保证需求分析核心只依赖 `AgentGateway`。
- 保持中文内容和来源位置，不依赖 MiniOrder 源码或 GUI。

**Non-Goals:**

- 本变化不实现测试项、测试用例、Windows GUI 探索或测试执行。
- 本变化不重写已有测试设计、执行和报告平台，不直接修改 `D:\project\agent\examples` 的用户工作区。
- 本变化不把 Hermes 固化为不可替换的业务框架，也不实现第二套模型调用基础设施。
- 本变化不实现历史经验补全、知识库、人工编辑 UI 或 B/S 多用户平台。
- 首版不承诺 OCR、图片语义理解或 DOCX 内嵌流程图解析成功；未解析内容必须显式报告。
- 首版不实现 XLSX、CSV、PPT、PPTX、PNG、JPG、BMP 输入。

## Decisions

### 1. 以现有 testing_platform 为产品骨架

正式实现沿用 `testing_platform` 的 domain、application、ports、infrastructure 和 runners 分层。需求分析作为新的应用工作流接入已有任务、Runner 和 Artifact 边界；不会新增平行的 `src/requirement_analysis` 顶层系统，也不会复制一套 Agent、任务和产物抽象。

当前正式仓库尚未包含这些产品模块，实施时从 `D:\project\agent\examples` 有选择地迁移已验证代码并记录来源、基线提交或内容哈希。迁移后的代码由正式仓库管理，不能通过 `..\examples` 导入或在运行时读取兄弟目录。备选方案是直接以 `examples` 为产品仓库，但其当前存在大量未提交重构和历史产物，难以隔离本任务修改，因此不作为本轮默认路径。

### 2. Hermes 是首版 Agent 运行时，不是需求分析框架

复用现有 `HermesAgentGateway`、运行时解析、Profile 和 SkillRegistry，避免重复实现模型配置、调用和 Skill 加载。需求工作流只面向 `AgentGateway` 和结构化 Schema；Hermes 的模型、Profile、工具和原始响应信息作为运行证据记录。

如果 Hermes 在结构化输出、目标部署或合规验证中不满足要求，可以增加新的 Gateway Adapter，而无需修改 Document IR、需求模型、核验器和评分器。备选运行时包括 Codex、OpenAI-compatible API 或经批准的本地模型，但本变化不同时实现多个生产适配器。

现有平台使用 Python 3.11。新增 DOCX、PDF、Markdown 解析依赖在实施前通过 spike 确认许可证、中文保真、目标操作系统安装和离线部署条件；候选包括 `python-docx` 加 OOXML 对象清单、PyMuPDF、结构化 Markdown 解析器及 JSON Schema 校验库。

### 3. 扩展现有需求模型与 Schema Registry

保留 `SourceDocument`、`SourceReference`、`RequirementItem` 和 `ParsedRequirements` 的既有语义，在兼容迁移后扩展：

- `SourceReference` 增加 `segment_id` 和格式专属 locator；
- `RequirementItem` 增加对象、类别、条件、预期行为、信息性质、置信度和核验状态；
- `ParsedRequirements` 增加歧义、冲突、失败区域和追溯索引；
- 将已预留的 `PARSED_REQUIREMENTS` 正式注册到 Schema Registry；
- 为需求分析和修复增加独立 `AgentTaskType`，不复用 `TEST_DESIGN` 的业务语义。

采用版本化 Schema 和兼容测试，避免已有测试设计消费者因字段变化静默失效。

### 4. 建立版本化 Document IR

所有格式 Adapter 输出 `document-ir/v1`：

- `document_id`、文件哈希、格式和解析器版本；
- 按原始顺序排列的 `segment`；
- 每个片段的稳定标识、类型、文本或对象引用、来源定位、父级关系、顺序和解析状态；
- 文档级和片段级失败清单。

片段标识由文件哈希、来源位置和内容哈希稳定生成，运行时间等非语义数据不参与标识。需求分析只读取 Document IR，不直接读取原始文件。

### 5. 解析 Adapter 与对象清单分离

- DOCX Adapter 提取标题、段落和表格，同时枚举图片、公式、嵌入对象和关系；不能解释的对象仍形成失败或未知片段。
- Markdown Adapter 保留标题层级、区块顺序和行范围。
- PDF Adapter 首版只保证文本层和页面位置；扫描页或无法提取的页面进入失败清单，不静默调用不稳定 OCR。

这比“把文件转成一整段纯文本”多保留了来源和结构。备选方案是直接使用通用文档解析框架；只有在 spike 证明其三种格式输出满足相同契约时才替换 Adapter，不让框架决定下游模型。

### 6. 新增独立 Requirement Analysis Workflow 和专用 Skill

现有 `test-case-design` Skill 同时要求 plan、requirements 和 cases，适合作为历史参考与后续消费者验证，不作为 S1 的正式需求分析 Skill。新增专用 Skill，只输出需求基线、测试类型建议、歧义、冲突和核验信息。

1. **Section Extractor**：按章节窗口提取原子规则，输出 `requirement-candidate/v1`。
2. **Requirement Consolidator**：处理跨片段条件、重复、术语关系和文档冲突，输出 `requirement-baseline/v1`。
3. **Requirement Verifier**：核验来源支持、数值、单位、条件、字段完整性和重复性，输出 `verification-result/v1`。

每一步使用固定 JSON Schema 和冻结提示。核验器不删除或覆盖初始提取，只增加状态和问题。提取最多允许一次基于核验问题的修正运行；原始版本与修订版本都保留，防止无限自我修正。

测试设计工作流以后只消费锁定的 `ParsedRequirements`，不在 S1 内被改造成新的用例生成方案。备选方案是继续在 `test-case-design` 中一次生成需求和用例，虽然实现更短，但无法独立验收需求理解，也无法定位解析、提取、归并或判断错误。

### 7. 模型调用通过已有 AgentGateway 和任务边界

复用现有 AgentGateway、任务服务、Runner Registry 和 Artifact 边界。核心契约只规定输入、输出、预算和模型标识，不绑定某个供应商；首版默认使用 Hermes Gateway，测试使用 Fake Gateway 隔离模型非确定性。

本地运行入口需要支持“导出 Agent 输入包”和“导入 Agent 结构化结果”，使没有可自动调用模型接口的环境也能完成可审计实验。任何 Runner 都必须记录模型、提示版本、参数、重试、人工介入和原始响应哈希。

#### 无效来源证据的受限修复

确定性来源校验将不存在的片段标识、越过当前窗口的片段标识，以及有效片段标识下不连续或与片段文本错配的 `excerpt` 统一表示为带稳定错误码的 `CandidateSourceValidationError`。不得依据语义相似度在本地自动映射、删除 `excerpt` 或直接替换为最近片段。工作流保留原始模型响应和确定性校验错误，并允许对该窗口发起至多一次独立修复调用；修复输入限于原候选、错误详情和当前窗口中合法的 `segment_id` 清单及对应完整文本。

修复调用使用现有专用任务类型和提示，计入调用次数与 token 预算，记录输入、响应、版本与哈希。修复只能修改 `requirements` 和 `ambiguities` 中的 `source_evidence`；候选数量、顺序、标识、需求陈述、条件、预期行为、分类、信息性质和置信度必须与原响应一致。修复结果仍须经过窗口边界、摘录连续性、来源元数据恢复及完整候选校验；仍无效时该阶段明确失败，不做第二次修复、不丢弃候选、不静默改写语义。该机制不放宽正式需求证据标准；协议、提示、预算或执行语义变化必须在新轮次冻结。

### 8. 真值与分析运行隔离

正式 Agent 可见输入只包含冻结样本、通用输出规范、正确的运行说明和预算。真值、匹配表、历史工作簿、具体答案和评分日志保留在评估侧，并由评估进程在原始报告锁定后使用。当前首版是目录、进程和独立上下文隔离，不宣称 OS 级安全沙箱。

### 9. 明确材料角色并使用互补评估集

- `CS-Autonomous-Testing-Framework-v0.1.md` 是项目建设主需求，决定 S1 目标和验收边界，不作为解析准确率样本计分。
- MiniOrder Markdown 是已知中文校准材料，只用于调通流程。
- `技术要求.docx` 是开发验证材料，用于检查 DOCX、复杂需求和指标表达。
- `D:\project\agent\examples` 的历史 XLSX 和 benchmark 是回归及差距分析证据，不作为真值答案提供给正式 Agent。
- 格式等价集以同一需求的多格式版本隔离格式解析差异；语义盲测集使用未参与提示和实现调整的独立资料评估提取质量。

现有 `validate_requirement_extraction.py` 的需求 ID、覆盖和禁止词检查保留为快速回归，但正式评分新增精确率、召回率、F1、来源定位、无依据输出和关键保真错误，并保留逐条匹配依据。

### 10. 对后续阶段使用去重来源投影并限制输入大小

v3 正式运行在归并阶段把完整 Document IR 与全部候选一并发送，造成输入约 847,923 字符、运行时估算约 213,637 token，超过 131,072 token 上限。只读测量显示，该运行有 657 次候选来源引用、411 个唯一来源片段；完整 IR 约 506 KB，而这些唯一来源片段及其来源元数据约 49 KB。只发送候选加去重来源投影，预计请求约 354,147 字符，较原归并请求减少约 58%。

归并、语义核验、修订和修订后核验根据候选/基线 `source_evidence.segment_id` 从本地 Document IR 构造去重来源投影；Document IR 仍保留给确定性校验和运行产物。工作流统一在 Gateway 调用前按 `len(user_input) + len(system_context)` 检查 450,000 字符上限。超限输入完整保留为拒绝证据并明确失败，不做截断、丢弃来源或自动拆分；检查发生在 BudgetedGateway 之前，因此不计模型调用和 token 用量。

### 11. 分块产出与确定性跨块组装

v4 证明 377,093 字符的去重来源归并输入能够通过上下文限制，但单次完整基线输出达到长度上限：首段已有 JSON 语法错误，续写也未从截断结构继续。不能通过补逗号或拼接猜测恢复缺失语义，因此大型材料改为有界产出，而不是继续提高输出上限或依赖续写。

1. 按候选窗口原始顺序，以冻结的候选批数上限建立归并块。每块调用现有 Requirement Consolidator，只看到本块候选与去重来源，输出一个可独立校验的 `requirement-baseline/v1` 片段。
2. 本地按块号和块内顺序将需求编号规范化为全局稳定编号，并同步更新歧义、冲突、推荐和追溯索引。该步骤只改标识和引用，不改需求语义或来源。
3. 新增 `requirement-reconciliation/v1`。跨块 Agent 输入只含规范化需求摘要，不含完整 Document IR；输出包括合并组、冲突对和术语歧义。合并组必须给出成员编号、保留编号和合并后的单条需求；其来源只能是成员来源的并集，不能引入新来源或未引用编号。
4. 本地验证每个操作引用已知编号、同一需求最多参与一个合并组、数值冲突不能作为同义合并，并按固定顺序应用操作。未参与操作的需求和块内结果原样保留；冲突、歧义的来源由成员需求确定性汇总。
5. 语义核验按冻结的需求条数上限切块。每块携带完整基线哈希、需求子集及其去重来源；所有结果合并前必须证明每个需求恰好有一个发现。v5 正式运行不执行自动基线修订，以避免在同一协议中再引入大型修订输出；确定性和语义核验发现直接进入锁定报告及评分，质量门槛不降低。

分块大小、跨块 Schema、提示、调用预算和禁用自动修订均在 v5 正式运行前冻结。任何块失败均使整次运行失败；不允许只组装成功块、手工补齐模型输出或对部分结果评分。

### 12. v5 失败后的 v6 边界

v5 在第 6 个提取窗口返回了结构有效的候选，但有 3 处 `excerpt` 与所引用的有效片段文本错配。模型调用、预算和运行环境均正常，确定性校验正确拒绝响应；失败原因是受限来源修复只捕获片段缺失或越界，没有捕获摘录连续性错误。v6 只扩展上述来源证据错误的修复入口，不改变候选 Schema、分块归并、跨块裁决、确定性组装、语义核验或评分门槛。

实现前先使用不计分的固定响应验证摘录错配修复成功、修复后仍错、越过窗口、语义被改写和预算耗尽。不得用 v5 锁定响应做手工补丁或部分评分。原 `DDS&MQTT` 材料已参与 v1 至 v5 诊断并直接推动 v6 设计，只能作为回归材料验证同类阻塞是否消除；后续正式泛化验收必须另选合法且未参与开发的新材料，由评估侧先冻结独立真值、匹配规则、预算和隔离清单。

## Risks / Trade-offs

- **[现有平台位于脏工作区]** → 只读盘点后有选择迁移，记录来源和哈希；不在原目录实施，不覆盖用户未提交修改。
- **[选择迁移可能造成短期重复文件]** → 只迁移本变化实际依赖的最小模块，并在正式仓库形成唯一运行时来源；不做全仓复制。
- **[现有消费者依赖旧 ParsedRequirements 字段]** → 使用 Schema 版本和兼容测试，禁止静默破坏测试设计工作流。
- **[Hermes 结构化输出能力不足]** → 先通过 AgentGateway/Fake Gateway 契约测试和小样本验证；必要时只替换 Gateway Adapter。
- **[不同格式的来源位置不可完全统一]** → Document IR 使用格式专属 locator，并提供统一的文件、片段和顺序字段，不强迫伪造页码。
- **[PDF 文本顺序可能与视觉阅读顺序不同]** → 保存页面坐标和解析器版本，在格式等价集中单独比较；无法可靠排序时标记限制。
- **[通用解析库遗漏图片、公式或嵌入对象]** → 同时生成对象清单，未解释对象进入失败报告，不把缺失当作无需求。
- **[模型结果非确定]** → 冻结模型和参数，记录原始响应，限制重试，并分别报告单次结果与必要的重复运行结果。
- **[第二轮核验可能形成自我确认]** → 使用独立上下文和只核验不看真值的提示；正式评分仍由评估方真值完成。
- **[精确率和召回率的匹配存在人工判断]** → 运行前冻结原子化及部分正确规则，保留逐条匹配表，并对争议项单独裁决。
- **[首版本地工作流不是最终 B/S 产品]** → 保持应用层和数据契约独立，后续服务化复用契约；本轮不宣称满足部署和并发条款。
- **[分块可能漏掉跨块关系]** → 使用独立跨块裁决阶段扫描全部规范化需求摘要；保留块内关系，并在正式评分中如实反映仍可能发生的漏检。
- **[确定性组装错误会改变模型语义]** → 组装代码只执行编号规范化、来源并集和经 Schema 校验的显式操作，并用顺序稳定性、未知编号、重复消费、数值保真和来源边界测试约束。

## Migration Plan

1. 冻结 `D:\project\agent\examples` 的复用清单、来源版本或内容哈希、现有测试结果和工作区状态，不对其写入。
2. 在正式仓库迁移最小 `testing_platform` 骨架及依赖测试，先证明迁移前后行为一致。
3. 扩展现有需求模型、Schema Registry、任务类型、文档层和独立 Requirement Analysis Workflow。
4. 用 MiniOrder Markdown 完成校准，再用 `技术要求.docx` 完成开发验证和历史基准回归。
5. 将已经参与流程调整的 `DDS&MQTT` 材料降级为回归材料；另选合法且未参与开发的新样本，冻结真值、匹配规则和正式盲测协议后运行验收，未达到门槛时保留失败结果并定位责任层。
6. 通过首期三格式验收后，后续变化按同一 Adapter 契约增加其余七种格式。
7. 回滚时只移除或撤销本变化迁入及新增的模块；MiniOrder、历史实验和 `examples` 用户工作区不受影响。

# 技术设计

## 背景与约束

当前仓库只有 Trellis/OpenSpec 基础结构和研究文档，没有产品代码或既定应用架构。本机提供 .NET SDK 9.0.312、Windows Desktop Runtime 8/9 和 WinForms 模板。现有 CUA 证据表明，标准 WinForms 控件能够提供比 Qt Canvas 更完整的 UI Automation 语义；已有 WinForms 示例只是控件验证样本，不包含可复用的订单业务领域。

变更动机见 `proposal.md`，可观察行为见两份能力规格。

## 目标与非目标

**目标：**

- 将样本保持在足够小的范围，使实验失败可以归因于 AI 测试流程，而不是复杂基础设施。
- 使用稳定的标准控件、明确标签、固定焦点顺序和可访问名称，使 UIA 可以识别，同时仍支持截图和鼠标键盘操作。
- 使业务规则具有确定性，并可在 GUI 之外独立验证。
- 从同一代码库构建正确基线和两个缺陷版本，不向黑盒测试方显示版本身份。
- 使每轮实验从隔离目录中逐字节一致的种子数据开始。

**非目标：**

- 开发自主测试 Agent、规划器、执行器封装、证据存储或报告生成器。
- 支持多操作系统、服务端部署、多用户并发、身份认证、订单编辑、订单删除或状态流转。
- 提供生产级安全机制、本地化基础设施、安装程序、自动更新或通用实验样本框架。

## 技术决策

### 1. 使用 .NET 8 WinForms 和标准控件

样本以 `net8.0-windows` 为目标框架，使用 `TabControl`、`TextBox`、`Button`、`ComboBox`、`DataGridView`、`ErrorProvider` 和 `StatusStrip` 等 WinForms 标准控件。控件具有稳定且中性的 `Name` 和 `AccessibleName`，但不提供仅供自动化使用的后门。

选择 WinForms 的原因是：本机 SDK 无需第三方依赖即可构建，Windows 10 原生支持，标准控件能够公开适合第一阶段实验的 UIA/MSAA 信息。WPF 会增加 XAML 和绑定复杂度，但不会改善本轮所需流程；Qt 会引入部署依赖，并重复已经观察到的自定义控件风险；Electron/WebView 更接近浏览器自动化，不适合作为最小原生 C/S 样本。

### 2. 将样本放在独立的仓库子目录

源码位于 `samples/MiniOrder/`，solution 包含：

- `MiniOrder.Core`：领域记录、校验、计算、编号和 JSON 持久化。
- `MiniOrder.App`：WinForms UI 和应用启动入口。
- `MiniOrder.Verification`：不依赖第三方测试框架的命令行验证程序，用于验证正确基线和缺陷版本契约。

MVP 阶段将样本保留在本仓库中，便于追溯。它不依赖未来的 Agent 代码；如果后续实验治理要求更强的访问隔离，可以再迁移到独立仓库。

### 3. 使用本地 JSON 存储和原子替换

每次运行使用显式指定的数据目录。应用读写一个 UTF-8 JSON 文档，其中包含 schema 版本和订单数组。保存时先写入临时文件，再原子替换当前文件，避免写入失败时留下不完整的序列化数据。

评估方使用本轮专属数据目录启动 MiniOrder。每次实验前，由 AI 可见包之外的样本命令使用版本化种子文档替换该目录。MVP 选择 JSON 而非 SQLite，是因为 JSON 不需要额外包、原生 DLL、迁移工具或数据库检查工具。

### 4. 使用紧凑的双页工作界面

主窗口包含“新建订单”和“查询订单”两个页签。新建页包含带标签的输入字段、只读金额、保存和清空命令、行内校验及状态消息。查询页包含关键字/状态筛选、查询和清除筛选命令、只读结果表格及结果数量。

布局保持普通且面向任务，不使用自绘界面、仅图标命令、隐藏手势、模态成功对话框或随状态改变尺寸的控件。校验错误可通过行内文本、可访问性信息和焦点移动三种方式观察。

### 5. 通过显式构建属性编译不同版本

`MiniOrderVariant` 是必需构建属性，允许值为 `Baseline`、`VariantA` 和 `VariantB`。编译期符号在每个缺陷版本中只改变一个策略点：

- `VariantA`：错误地允许数量 0。
- `VariantB`：错误地使用数量加单价，而不是数量乘单价来计算金额。

三个版本的 UI、程序集产品名、可执行文件名、版本文本、种子格式和常规日志保持一致。版本选择不从运行时配置读取，避免实验期间意外切换。构建脚本遇到未知版本值时必须失败。

### 6. 分离源码、评估方资产和 AI 可见包

仓库源码和评估方文件可以标明版本名称，因为它们属于私有 Ground Truth。按照工作区产物管理规则，构建输出写入 `artifacts/miniorder/`：

```text
artifacts/miniorder/
  distributions/
    baseline/
    variant-a/
    variant-b/
  blackbox-run/
    MiniOrder.exe
    MiniOrder.runtimeconfig.json
    MiniOrder-Requirements.md
  diagnostics/
```

staging 命令每次只将一个选定发行包以中性名称复制到 `blackbox-run/`，并使用 allowlist 校验目录。源码、PDB 文件、评估工具、缺陷清单、脚本和验证输出均不得进入该目录。

### 7. 保持需求与 Ground Truth 独立

`docs/miniorder/MiniOrder-Requirements.md` 是面向用户的中文规格，只包含可观察规则；当示例可能泄露植入缺陷时，不在需求中给出该示例。仅供评估方使用的 `evaluation/miniorder/defect-manifest.md` 将每个私有版本映射到被违反的需求和预期证据。验证程序独立于 GUI 事件处理器实现同一组契约。

### 8. 分三个层级验证

1. 构建验证以 warnings-as-errors 编译全部项目。
2. 核心验证针对 `Baseline` 运行完整正确契约，确认每个缺陷只在其对应版本中被检出，且无关契约继续通过。
3. GUI 冒烟验证在 Windows 中启动每个中性交付包，并使用 CUA 验证窗口发现、UIA 树可见性、创建/保存/查询流程、重启持久化和重置行为。截图和日志写入 `artifacts/miniorder/diagnostics/`。

应用本身不暴露测试 API。GUI 冒烟验证只观察普通用户可见状态，与黑盒 Agent 的观察边界一致。

## 风险与取舍

- **[WinForms 比许多真实 C/S 应用更容易被 UIA 识别]** -> 将 MiniOrder 作为第一个受控基准；只有在端到端测试契约验证有效后，再增加 Qt 或自定义 Canvas 样本。
- **[编译期缺陷分支在源码中仍可被发现]** -> 测试 Agent 只能在包含 staging 黑盒包的工作区中运行，不授予文件系统和源码仓库访问能力。
- **[依赖框架的发布方式要求 .NET Desktop Runtime 8]** -> staging 时检查运行时，并将其记录为评估环境前置条件；如果后续迁移到干净机器，再增加 self-contained 发布。
- **[本地日期会影响生成的订单编号]** -> 需求断言当前本地日期和流水号格式，而不固定完整编号；种子记录使用固定历史编号。
- **[JSON 不适合并发写入]** -> 每个数据目录只允许一个 MiniOrder 实例运行，并将并发排除在本次范围之外。
- **[隐藏的评估方重置入口可能通过不受限进程参数泄露]** -> 将重置程序和调用方式保留在 AI 可见包之外，并在授予 Agent GUI 权限之前启动 SUT。
- **[缺陷可能意外影响其他行为]** -> 运行契约矩阵，每个缺陷版本只允许出现一个指定失败，任何额外失败都使验证失败。

## 迁移与回滚

这是一个全新样本，不迁移现有数据或代码。实现只新增 MiniOrder 子目录及相关文档。回滚时移除 MiniOrder 子目录、对应 OpenSpec 变更和任务资产；`artifacts/miniorder/` 下的生成输出可重新构建，不得提交到版本库。

# MiniOrder 第二轮 UIA 独立盲测实验

## 目标

在 MiniOrder 程序、中文需求、固定种子、正式预算和评分权重不变的条件下，验证加入正确 Sky 工具入口、启动健康检查和通用争议证据核验规则后，新的独立测试 Agent 能否再次自主发现业务缺陷，并更准确地区分产品异常、工具异常和证据不足。

## 需求

### R1. 第一轮收尾

- 保留 round-01 全部原始报告、阻塞记录和锁定哈希。
- 新增收尾勘误，明确早期“全局服务故障”是当时判断，最终已确认原因为错误 REPL 通道。
- 记录任务、源码版本和未提交状态；不自动提交或归档。

### R2. 最小流程修正

- Computer Use 只在 `mcp__node_repl__js` 中导入 `@oai/sky`。
- 正式测试前验证工具初始化、真实窗口观察、一个无业务副作用动作和回读。
- 单个工具字段异常不能单独证明产品缺陷；冲突时使用另一种允许的 GUI 行为或观察核验，证据仍不足则输出 `INDETERMINATE`。
- 分开记录产品行为、工具观察、执行状态和最终判断，并保留争议过程。

### R3. 第二轮冻结与隔离

- 沿用同一中文需求、三个构建身份、固定种子、25 分钟/60 次 GUI 输入预算和冻结评分权重。
- 三个匿名目标在运行前私下重新映射，分别使用独立数据目录和不继承历史的 projectless 测试会话。
- 测试方不得获得源码、内部数据、真值、上一轮报告、具体触发步骤或预写业务用例。

### R4. 正式运行与锁定

- 每个 Agent 在首次业务操作前输出首批测试设计。
- 测试只经 GUI/UIA 执行；逐项记录执行状态及 `PASS / FAIL / INDETERMINATE`。
- 疑似缺陷自主复现，冲突证据自主核验；人工介入、重试、超时和预算完整记录。
- 每份原始报告保存并计算 SHA-256 后，评估方才揭示身份评分。

### R5. 独立评估

- 沿用设计 20、执行覆盖 25、证据 20、结论 20、复现/无缺陷判断 10、自主性 5 的固定权重。
- 分别统计目标完成率、两个已知缺陷的检出/漏检、产品误报、证据不足、争议自主核验、评估方介入和工具阻塞。
- 与 round-01 比较时明确统计范围；未触发争议场景不能算作争议机制已验证。

## 验收标准

- [x] AC1：round-01 勘误和索引完成，锁定报告哈希不变。
- [x] AC2：round-02 协议、基线、匿名映射、隔离说明和提示在正式运行前冻结。
- [x] AC3：最小健康检查通过，或以工具/环境阻塞证据停止。
- [x] AC4：三个正式目标使用互相独立的新测试上下文，报告全部锁定。
- [x] AC5：评估在揭示真值后完成，未事后修改预算、权重或统计口径。
- [x] AC6：最终报告明确区分第一轮收尾、修正验证、第二轮完成情况及有限能力结论。

## 范围外

- 修改 MiniOrder 业务、需求、种子或受控缺陷。
- 视觉路径、多 DPI、RDP、无人值守或其他软件。
- 新建通用测试平台、服务或执行器。
- 自动提交、推送、合并、发布或通过 Trellis 归档产生提交。

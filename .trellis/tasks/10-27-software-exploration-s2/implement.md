# 第二阶段软件探索能力验证执行计划

## 1. 冻结基线和评估真值

1. 核验 Git 状态、MiniOrder Baseline、中文需求、S1 校准基线、种子和历史锁定证据哈希。
2. 建立 S2 评估真值映射，覆盖关键入口、页面、控件、可观察状态、允许路径和非 GUI 需求分类。
3. 独立复核真值映射，解决分母、部分映射和语义等价规则争议。
4. 生成中性软件目录与两套独立数据目录，不修改历史黑盒目录和锁定证据。

验证门：输入和真值可以逐项追溯，目录不泄露版本身份，哈希已冻结。

## 2. 准备协议与输入包

1. 生成 S2-A 人工核验需求包。
2. 从锁定 S1 MiniOrder 基线生成 S2-B 中性交付包，记录脱敏/裁剪规则和前后哈希。
3. 编写测试 Agent 通用提示、输出模板、隔离清单和评分规则。
4. 冻结 15 分钟/30 动作预算、恢复次数、结束条件和建议质量门槛。

验证门：测试方材料不含 UI 真值、旧路径、源码、缺陷信息、版本身份或预写探索答案。

## 3. UIA 健康检查

1. 按 `computer-use` 技能读取运行指导和确认规则。
2. 在独立诊断上下文初始化 `@oai/sky`，唯一定位匿名 MiniOrder 窗口。
3. 完成页签往返并重新观察 UIA，确认真实窗口、输入动作和状态回读可用。
4. 核验数据目录没有业务变化，锁定健康检查报告。

验证门：健康检查通过才启动 S2-A；失败则记录环境阻塞并停止。

## 4. S2-A 软件探索本体验证

1. 重置独立数据目录并启动匿名 Baseline。
2. 创建全新测试上下文，只提供 S2-A 输入包、通用提示和允许工具。
3. 执行需求驱动探索，原始报告写入独立产物目录并锁定。
4. 锁后对照真值评分，记录映射正确、部分、错误、漏映射、不可观察和工具阻塞。

验证门：S2-A 报告锁有效，评分分子/分母可复核，未发生持久化副作用。

## 5. S2-B S1 连接验证

1. 使用另一独立数据目录和全新测试上下文，禁止继承 S2-A 结果。
2. 只提供 S1 真实基线中性交付包、相同通用提示和工具边界。
3. 执行并锁定探索报告，记录 S1 输入中歧义、重复或颗粒度对映射的影响。
4. 锁后评分，并与 S2-A 比较信息丢失、扩大、映射成本和错误归因。

验证门：S2-B 结果独立，比较不改写任何一轮原始报告或冻结规则。

## 6. 总体评估与质量检查

1. 汇总健康检查、S2-A、S2-B、人工介入、预算和隔离审计。
2. 明确每个建议门槛是否达到，不以平均分覆盖失败。
3. 运行 JSON/UTF-8/锁完整性检查、相关单元测试、OpenSpec strict 和 Trellis check。
4. 输出受控能力结论、限制和 S3 的最小输入建议；不自动进入 S3。

## 主要风险点

- 旧 MiniOrder 实验答案泄漏给新测试上下文。
- S1 真实基线包含本机路径、运行元数据或过细需求，需中性化但不能改语义。
- 探索动作越界成为业务测试或持久化修改。
- UIA 首次快照不完整、旧索引失效或截图超时被误判成软件入口不存在。
- 评估真值根据源码生成时把内部实现细节误当作黑盒必见控件。

## 回滚点

- 规划和实验资产进入新的 S2 目录，不覆盖 S1 与 MiniOrder 历史报告。
- 任一运行失败保留原目录和锁，新尝试使用新运行标识。
- 不使用 `git reset --hard`，不修改或重建 MiniOrder。

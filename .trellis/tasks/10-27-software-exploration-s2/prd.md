# 第二阶段软件探索能力验证

## 目标与用户价值

验证测试 Agent 能否在不知道源码和实现答案的前提下，根据已经核验的需求，自主观察陌生 Windows C/S 软件，找到功能入口、控件、可达状态和非破坏性操作路径，并建立可追溯的“需求 -> 界面证据”映射。先单独证明软件探索能力，再把它交给后续测试设计阶段；不把旧的端到端测试结果改名为 S2 成绩。

## 已确认事实

- `CS-Autonomous-Testing-Framework-v0.1.md` 将 S2 定义为“把需求对应到陌生软件入口、路径与状态”，输出探索轨迹、映射、不可达与未知项。
- S1 已完成并归档。MiniOrder 校准运行 `3960ded9-e5fc-4079-a214-d9ee43e4a74f` 产生 24 个文档片段、52 条需求、8 条歧义和 10 条测试类型推荐，确定性核验无发现，52/52 条语义核验为 supported；该结果属于校准输出，不是人工真值准确率。
- MiniOrder 正确基线 EXE 的 SHA-256 为 `62105E53AA16B042BC86168F4D420D9FC4CCD012B75CF27F7048786C79534B15`，中文需求 SHA-256 为 `033BEE6C01FE24DDAE53D449B309F44B470A864CDD4583BB4BD7B17B4FDC603F`。
- 现有 UIA 证据确认两个页签、关键字段、按钮、状态和查询控件可识别；正确工具入口为 `mcp__node_repl__js + @oai/sky`。截图通道曾持续超时，按钮几何和首次切页快照存在已知限制。
- MiniOrder round-01/02 同时验证了需求理解、测试设计、执行和判断，不能替代独立 S2 验收；三个构建的 UIA 树相同，因此 S2 重复探索两个缺陷版不会增加有效证据。
- 当前仓库没有独立的软件探索模块。首轮应复用现有 Computer Use 能力，不新建通用探索框架、不接入 UFO、FlaUI、Squish 或新服务。
- MiniOrder 已参与历史工具和流程调整，本轮只能证明受控样本上的 S2 方法与连接，不能宣称对其他 Windows C/S 软件的泛化能力已经通过。

## 需求

### R1. 冻结输入与评估依据

- 只使用 MiniOrder 正确基线构建；冻结 EXE、需求输入、固定种子、数据目录、工具版本、提示、预算和环境哈希。
- 评估方在正式运行前建立并锁定需求到页面、控件、可观察状态和允许路径的真值映射；真值可依据源码、UIA 冒烟和人工复核生成，但不得提供给测试 Agent。
- 已有报告和锁定证据不得覆盖；新的健康检查、运行和裁决使用独立目录。

### R2. 两层独立验证

- S2-A 使用评估方核验过的需求集合，隔离上游误差，评价软件探索本身。
- S2-B 使用 S1 的真实 MiniOrder 需求基线，评价 S1 -> S2 连接中的信息保留、扩大和丢失。
- S2-A 与 S2-B 使用不同、未继承历史和彼此结果的测试上下文，分别从相同固定初始状态开始。
- 两次运行的分数和错误必须分别报告，不用平均分掩盖某一层失败。

### R3. 测试方边界与安全探索

- 测试 Agent 只能获得本次需求输入、已启动的匿名软件窗口、允许的 Computer Use/UIA 规范、运行预算和输出格式。
- 禁止读取源码、文件系统、内部数据、旧实验报告、真值、契约矩阵、缺陷清单、版本身份、预写路径和操作答案。
- 允许 UIA 树、控件属性、焦点、选中状态、标准键盘和界面内的非破坏性导航；必要的瞬时输入必须不触发保存并在结束前清除。
- 禁止保存、删除、修改持久化业务数据，以及运行缺陷触发用例；S2 只识别入口、路径和状态，不判断业务 PASS/FAIL。
- 找不到入口不等于功能不存在。工具超时、定位失败、不可观察、需求本身非 GUI 可验证以及预算未覆盖必须分别记录。

### R4. 探索输出与追溯

- 在首次 GUI 动作前形成需求驱动的探索计划，列明目标需求、拟观察界面、动作风险和证据方式。
- 每一步记录前置界面、动作、动作后回读、工具状态、是否产生副作用以及关联需求。
- 建立窗口、页面/区域、控件、可见状态和允许动作的界面清单，并给出稳定的可识别属性；不得依赖已失效的旧元素索引。
- 每条需求使用 `MAPPED`、`PARTIALLY_MAPPED`、`NOT_UI_OBSERVABLE`、`UNREACHABLE` 或 `INDETERMINATE`，附入口、路径、状态、证据和理由。
- 输出未知控件、未映射需求、不可达路径、工具限制和风险动作清单；不得把程序实际显示内容反写成需求预期。

### R5. 冻结预算、指标与结束条件

- 每次正式运行最多 15 分钟或 30 次 GUI 输入动作，以先到者为准；同一失败动作最多重试 2 次，窗口重新绑定最多 1 次。
- 正式运行前用独立诊断上下文完成工具初始化、真实窗口观察、无业务副作用的页签往返和回读；健康检查不计分且不得暴露探索答案。
- 预注册指标至少包括：关键功能入口召回率、UI 相关需求映射召回率、映射精确率、路径可复现率、状态/工具分类正确率、无依据控件比例、持久化副作用和人工介入次数。
- 本轮建议门槛为：两个关键功能入口召回率 100%，UI 相关需求映射召回率不低于 90%，映射精确率和可复现路径比例均不低于 95%，无依据控件不高于 5%，持久化副作用为 0。
- 预算耗尽、连续工具恢复失败、全部计划完成或出现不可接受副作用风险时停止；不足证据保留为 `INDETERMINATE`。

### R6. 锁定、评估与结论范围

- 原始探索报告锁定后，评估方才能读取真值评分；裁决和勘误新增记录，不改写测试方原始报告。
- 评估分别说明需求计划覆盖、实际观察覆盖、正确映射、错误映射、漏映射、不可观察、不可达、工具阻塞和人工介入。
- 若 S2-A 通过而 S2-B 失败，优先归因上游连接或输入可用性；若两者都失败，不能用 S1 成绩替代 S2。
- 本轮通过只表示 MiniOrder、当前 Windows 主机、当前 UIA 文本路径和冻结预算下的受控验证通过；不外推视觉路径、其他技术栈、RDP、多 DPI、无人值守或独立产品部署。

## 验收标准

- [x] AC1：冻结基线、评估真值、协议、隔离清单、提示、预算及工具环境均在正式运行前生成哈希并锁定。
- [x] AC2：独立健康检查完成“观察真实窗口 -> 非破坏性动作 -> UIA 回读”，且未修改业务数据。
- [x] AC3：S2-A 在独立测试上下文完成需求驱动探索并锁定原始报告，所有正式映射均有 GUI/UIA 证据。
- [x] AC4：S2-B 在新的独立上下文消费 S1 真实基线并锁定原始报告，不继承 S2-A 路径或答案。
- [x] AC5：两次运行均明确区分界面事实、工具观察、执行状态和映射结论，没有把工具失败或找不到入口当作产品缺陷。
- [x] AC6：评估在锁后完成，逐项给出指标分子、分母、漏映射和错误映射；S2-A 的门槛失败已如实保留。
- [x] AC7：没有保存、删除或修改持久化业务数据，没有读取测试方禁止材料，人工提示与恢复全部留痕。
- [x] AC8：最终结论明确区分“样本/工具就绪”“S2-A 完成”“S2-B 完成”“受控能力支持”和“跨软件泛化尚未验证”。

## 不在范围内

- 测试项和测试用例生成、边界值执行、业务 PASS/FAIL、缺陷发现与复现。
- 修改 MiniOrder 业务、需求、种子、历史锁定报告或三个发行构建。
- 新建通用探索框架、执行器封装、服务、数据库或 B/S 界面。
- 引入、安装、升级或对比 UFO、FlaUI、Squish、TESTAR 等长期依赖。
- 视觉路径、多 DPI、RDP、无人值守、其他 Windows 软件和整体 S7 闭环验收。

## 延后但不阻塞本轮的问题

- MiniOrder 是受控且 UIA 友好的已知样本；S2 泛化验收仍需一套此前未参与流程调整、同时具备合法需求和评估真值的陌生软件。
- 原始《技术要求》没有给出 S2 独立门槛，本任务中的百分比是实验前建议门槛，必须经用户确认后冻结，不能称为原文件指标。

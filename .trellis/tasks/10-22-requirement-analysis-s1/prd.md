# 第一阶段需求解析能力

## 目标与用户价值

在现有 `testing_platform` 基础上建立测试系统的第一阶段需求解析能力：将 DOCX、Markdown、PDF 需求资料转换为可追溯的统一内容，提取并核验原子需求和测试类型建议，为后续测试设计提供可信需求基线。先证明需求理解正确，再扩展格式、测试项、用例和 GUI 执行能力。

## 已确认事实

- `CS-Autonomous-Testing-Framework-v0.1.md` 是项目建设主需求基线，决定 S1 范围和能力目标；它不是需求解析正式盲测样本。
- `D:\project\agent\examples` 已有 Python 3.11 `testing_platform`、需求模型、AgentGateway、Hermes Gateway、SkillRegistry、测试工作流、任务与产物边界，可作为本阶段直接复用和扩展的技术基础。
- 现有需求读取仅支持 DOCX/Markdown/TXT 并压成纯文本；现有 `test-case-design` 把需求提取和用例生成混在一起，不能代替独立需求理解验收。
- Hermes 只承担首版可替换 Agent 运行时；需求分析核心依赖 AgentGateway，不绑定 Hermes 内部实现。
- `D:\project\agent\examples` 存在大量用户未提交修改，本轮只读盘点并有选择迁移，不直接在其中开发，不建立运行时兄弟目录依赖。
- 用户已确认首期只支持 DOCX、Markdown、PDF，流程稳定后再扩展其余七种格式。
- 用户已确认本阶段输出原子需求基线和测试类型推荐，不生成测试项或测试用例。
- 历史经验补全默认关闭，避免把外部经验混入基础提取准确率。
- MiniOrder Markdown 仅作校准，`技术要求.docx` 仅作开发验证，历史 XLSX/benchmark 仅作回归证据，均不计正式盲测泛化成绩。

## 需求

### R1. 文档摄取

- 冻结输入文件名称、格式、长度、SHA-256、配置和组件版本。
- 将 DOCX、Markdown、PDF 转换为版本化统一片段，保留顺序、结构和格式专属来源位置。
- 图片、公式、扫描页、嵌入对象等未解析内容必须显式记录，不能当作不存在需求。
- 相同输入、配置和版本重复运行时，片段标识、顺序和内容哈希应稳定。

### R1A. 现有平台复用

- 沿用 `testing_platform` 的分层、需求模型、AgentGateway、SkillRegistry、任务、Runner 和 Artifact 边界，不新增平行框架。
- 扩展现有 `ParsedRequirements`、`SourceReference` 和 Schema Registry，新增独立 Requirement Analysis Workflow 与专用 Skill。
- 正式实现必须进入当前正式仓库，不得通过 `..\examples` 导入或读取兄弟目录。
- 迁移前后通过既有测试和兼容夹具验证行为一致，不覆盖 `examples` 中的用户修改。

### R2. 原子需求基线

- 提取测试对象及功能、性能、接口、边界、安全、约束和异常信息。
- 保持数值、单位、比较关系、条件、例外和异常行为，不确定时记录歧义。
- 每条正式需求必须引用来源片段，并区分原文明示、推导、历史补全和无依据假设。
- 合并同义重复，保留多来源；对冲突内容保留双方，不自动裁决。
- 根据需求推荐测试类型，推荐与原始需求分开记录。

### R3. 独立核验与交付

- 确定性核验来源、字段、数值、单位、重复和失败片段引用。
- 独立语义核验使用 supported、partially_supported、unsupported、indeterminate，不覆盖初始提取。
- 交付输入、片段、失败、需求、歧义、冲突、测试类型、核验和追溯索引。
- 本阶段不得把测试项或测试用例作为正式输出。

### R4. 评估与隔离

- 运行记录必须区分项目建设需求、校准样本、开发验证样本、历史回归证据和正式盲测样本。
- 正式运行前冻结输入、真值、匹配规则、部分正确规则、预算和指标口径。
- 正式 Agent 不得获得真值、历史答案、软件实现和评估日志。
- 原始输出锁定后评分；不得为提高成绩修改输出或规则。
- 精确率、召回率、F1、来源定位、无依据输出和关键保真错误必须分别报告。

## 验收标准

- [x] AC1：DOCX、Markdown、PDF 均能生成可回查来源的统一片段，所有未解析区域均显式报告。
- [x] AC2：相同基线重复运行的片段标识、顺序和内容哈希一致。
- [x] AC3：原子需求、测试类型、歧义、冲突和核验结果符合冻结 Schema，且可追溯到输入片段。
- [x] AC4：核验过程保留初始结果和争议，工具或证据不足不会被误记为正确需求。
- [x] AC5：MiniOrder 与《技术要求》预演完成并分别报告解析、提取和核验问题，但不计正式泛化成绩。
- [x] AC6：正式盲测中功能、性能、接口需求精确率和召回率分别不低于 80%，来源定位有效率不低于 95%，无来源支持的正式需求不高于 5%，关键数值、单位和合法边界错误为零。
- [x] AC7：实现和实验不修改 MiniOrder 业务、需求、种子或已锁定报告，OpenSpec strict validation 与 Trellis 校验通过。
- [x] AC8：正式仓库复用已验证的 `testing_platform` 边界，迁移兼容测试通过，运行时不依赖 `D:\project\agent\examples`，且该目录的既有用户修改保持不变。

## 不在范围内

- 测试项、测试用例、GUI 探索、测试执行和缺陷判断。
- 历史知识库、经验补全、人工编辑 UI、B/S 多用户平台。
- XLSX、CSV、PPT、PPTX、PNG、JPG、BMP 输入。
- 用本轮结果宣称十种格式、多模态或完整产品要求已经通过。

## 延后但不阻塞实现的问题

- 正式语义盲测材料由用户提供，或由评估方选择合法且开发 Agent 未见过的资料；必须在正式实验冻结前确定。
- 模型 Runner 和解析依赖的具体版本由实施前 spike 根据许可证、中文保真和 Windows/Linux/Kylin 兼容性确定。

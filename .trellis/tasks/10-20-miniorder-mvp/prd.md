# MiniOrder MVP 验证软件

## 目标

构建一个最小、可重复、可隔离的 Windows C/S 订单管理样本，用于验证 AI 能否仅根据独立需求文档和可运行软件，自主设计测试、操作 GUI、收集证据，并发现两个预先植入且可独立归因的缺陷。

## 用户价值

MiniOrder 将把“Agent 是否能做自主黑盒测试”变成一个有确定需求、正确基线、缺陷 Ground Truth 和重置机制的实验，而不是把 GUI 操作成功误当成测试成功。

## 已确认事实

- 仓库目前没有产品代码、现成订单程序或既定应用架构，只有 Trellis、OpenSpec 和研究文档。
- 当前 Windows 10 x64 环境安装了 .NET SDK 9.0.312、Microsoft Windows Desktop Runtime 8/9 和 WinForms 模板，不需要安装第三方依赖即可开发。
- `D:\project\agent\cua-validation` 提供可复用的 CUA 验证经验和 WinForms 控件样例，但没有可直接作为 MiniOrder 使用的业务程序。
- 既有验证表明标准控件可通过 UI Automation 观察和操作，而 Qt 自绘区域及截图链路存在更大不确定性。
- OpenSpec 变更 `build-miniorder-mvp` 已定义完整行为规格、技术设计和实施任务，并通过严格校验。

## 需求

### R1. 订单工作流

- 应用提供中文 Windows 桌面界面，包含“新建订单”和“查询订单”两个主要工作区。
- 新建订单包含客户名称、商品名称、数量、单价和只读订单金额。
- 客户和商品为必填项，去除首尾空格后长度为 1～50 字符。
- 数量必须是 1～999 的整数。
- 单价必须是 0.01～999999.99、最多两位小数的十进制金额。
- 数量和单价有效时，金额实时显示为两者乘积并保留两位小数；任一输入无效时不得显示计算金额。
- 有效订单保存后只新增一条记录，编号格式为 `MO-yyyyMMdd-NNNN`，初始状态为“新建”。
- 查询支持按订单号、客户或商品关键字进行不区分大小写的包含匹配，并可叠加精确状态筛选。
- 查询结果显示订单号、客户、商品、数量、单价、金额、状态和创建时间。
- 使用同一数据目录重启后，已保存订单仍然存在。

### R2. 受控实验版本

- 生成三个独立发行包：正确基线、数量边界缺陷版、金额计算缺陷版。
- 数量缺陷版仅错误地允许数量 0；金额缺陷版仅错误地使用加法计算金额。
- 三个发行包的可见名称、窗口、控件、版本文本、普通文件名和业务流程一致，不向测试 AI 泄露变体身份。
- 未知变体参数必须使发行构建失败，不允许在运行时通过配置切换缺陷。

### R3. 可重复状态

- 每次实验使用独立数据目录。
- evaluator 可执行重置，将数据恢复为版本化的固定种子状态。
- 连续两次重置生成完全相同的数据哈希，并清除实验过程中新增的订单。
- MiniOrder 的正常业务流程不依赖网络、外部设备、数据库服务、管理员权限或新安装依赖。

### R4. 黑盒隔离

- AI 可见包只包含一个中性命名的可运行 MiniOrder、运行所需文件和独立中文需求文档。
- AI 可见包不得包含源码、PDB、缺陷清单、变体名、验证程序、预制测试用例、操作脚本或评估答案。
- 缺陷 Ground Truth、重置工具、校验矩阵、哈希和 evaluator runbook 保存在隔离的 evaluator 资产中。
- 测试时 evaluator 先重置并启动软件，再只授予测试 AI 需求文档和 GUI 观察/操作能力。

### R5. 验证要求

- 业务核心需有无第三方测试框架依赖的自动验证程序。
- 基线必须通过全部契约；每个缺陷版必须只失败于其目标契约，其他契约仍通过。
- 需用 CUA 完成创建、保存、查询、重启持久化和重置后的 GUI 冒烟闭环，并保留 UIA/截图或明确的工具限制证据。
- 构建、验证和诊断产物统一写入 `artifacts/miniorder/`，不得散落到共享项目父目录。

## 验收标准

- [ ] AC1: `dotnet build` 在 Release 配置且 warnings-as-errors 下成功，无需新增第三方 NuGet 包。
- [ ] AC2: 基线自动契约矩阵为 0 个失败；数量缺陷版只出现数量 0 契约失败；金额缺陷版只出现 `3 × 12.50` 应为 `37.50` 的契约失败。
- [ ] AC3: GUI 中可以完成有效订单保存、按关键字查回、查看“新建”状态，并在重启后读回相同数据。
- [ ] AC4: 空文本、超长文本、无效数量和无效单价均阻止保存，产生可观察的字段错误，且订单数不增加。
- [ ] AC5: 两次数据重置的 SHA-256 相同，且实验新增记录被清除；不同数据目录互不影响。
- [ ] AC6: 三个发行包普通 UI 身份一致，二进制哈希不同；缺陷不能通过运行时配置开启或关闭。
- [ ] AC7: AI 可见目录通过 allowlist 审计，不含源码、Ground Truth、脚本、验证工具、PDB 或变体提示。
- [ ] AC8: 中文需求文档覆盖全部可观察业务规则，且不出现实现技术、植入缺陷、预制测试步骤或评估答案。
- [ ] AC9: Windows CUA 冒烟测试形成“观察 → 操作 → 状态确认”证据；执行器失败与产品失败分别记录。
- [ ] AC10: 最终 readiness 报告明确列出构建版本、EXE 哈希、重置哈希、验证结果、已知限制和黑盒实验启动方式。

## 不在范围内

- 自主测试 Agent、Requirement Model、测试规划器、GUI Execution Adapter 封装、Evidence/Result 平台。
- 登录、权限、多用户、订单编辑/删除、状态流转、服务端、数据库服务、安装程序和自动更新。
- macOS/Linux、Qt/WPF/Electron 多技术栈对照和通用桌面应用框架。
- 把 MiniOrder 设计为生产订单系统或未来产品基础。
